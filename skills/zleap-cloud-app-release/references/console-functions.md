# 云函数与后台能力

这个面板管理三件相关的事：**云函数的声明**、**后台能力的授权**、**触发器的启用**。

页面顶部说明：「函数和后台能力都由应用 Manifest 声明，随签名版本一起部署到开发环境。」
下面有两个标签页：

| 标签页       | 内容                                                     |
| ------------ | -------------------------------------------------------- |
| **函数**     | 当前版本声明的云函数（只读展示）                         |
| **后台能力** | 每项后台能力的授权、试运行、运行记录，以及它名下的触发器 |

> **触发器在哪**（提示）
>
> 触发器没有单独的标签页。Manifest 里每个触发器只绑定一项能力，
> 所以它显示在**对应能力详情的「触发器」子标签**里。

（截图：云函数页，见文档站）

云函数页：安装还没绑定签名发布时提示「云函数还不能运行」（appid 应用正常情况下不会出现，见[还没激活时](#还没激活时)）；函数列表只读展示 Manifest 声明。

两个标签页只在**开发环境**下完整出现。切到**生产环境**时只剩只读的「后台能力」视图，顶部提示
「生产环境只读：可以查看本人后台能力的调用记录与结果；函数调试、授权和触发器请在开发环境操作。」
这里只显示**你本人**在生产环境的激活与调用记录（没有时显示「生产环境还没有你的调用记录。」）；
能力还没激活到生产时会提示该能力尚未在生产环境激活。

> **用命令行试调**（提示）
>
> `zleap-app invoke <app_id> --capability <能力 ID> --environment dev --input-file in.json --wait-seconds 25`
> 直接调用一项后台能力，返回调用编号和结果；之后用 `zleap-app invocation <app_id> <调用编号>` 查最新状态。
> 能力没在该环境启用时报 `CAPABILITY_NOT_ACTIVE`——开发工具不会代你允许后台运行。

## 云函数列表

「函数」标签页**只读展示**你作为发布者拥有的最新 Manifest 里 `runtime.backend.functions` 的声明。
看到函数列表 ≠ 函数能跑，也 ≠ 你授权了它。

### 还没激活时

当前安装还没有绑定已签名发布时，列表上方显示：

> **云函数还不能运行**

appid 应用上传时自动签名，安装、切换版本、保存权限时自动绑定（还没有就绪发布的版本会当场补签），正常情况下不会看到这条提示。
如果看到了，提示正文是「当前安装还没有绑定签名版本。带云函数的版本上传时由平台自动签名；到「后台能力」里允许后台运行（或在版本管理切换一次版本），平台会自动补签并绑定。」，
右侧按钮「**去允许后台运行**」切到本页「后台能力」，在那里允许后台运行即会补签并绑定，见[带云资源的应用自动签名与绑定](console-release.md#带云资源的应用自动签名与绑定)。

旧 `app_key` 应用的提示正文是「需要把签名版本激活到开发环境。」，右侧按钮「**去激活**」跳到[版本与激活](console-legacy-release.md)页完成激活开发。

### 函数表格

| 列               | 说明                                                                               |
| ---------------- | ---------------------------------------------------------------------------------- |
| **函数**         | 函数名（`functions[].name`），下方小字是入口，例如 `cloudfunctions/classifyTicket` |
| **运行环境模板** | `runtime_profile`，例如 `node-lts/1`                                               |
| **资源限制**     | `{内存} MB · {超时}s`，例如 `512 MB · 30s`                                         |
| **依赖**         | 函数用到的 Provider，没有时显示「—」                                               |
| **状态**         | 见下                                                                               |

状态标签：

| 标签               | 条件                                           |
| ------------------ | ---------------------------------------------- |
| **可调用**         | 声明有效、安装已绑定签名发布、函数运行环境可用 |
| 不可用原因（橙色） | 服务端给出了原因，见[不可用原因](#不可用原因)  |
| **已声明**         | 其他情况（例如还没激活）                       |

表格下方可展开「**Provider 声明**」，逐个列出 Provider 的 ID、类型和「已声明 / 不可用」。

### 空状态

「**当前活跃版本未声明云函数。**」下方附说明：「列表读取你作为发布者拥有的最新 Manifest v2，仅展示声明，不执行代码，也不会授予权限。」

### 运行环境不可用时

已激活、但函数运行环境不可用时，显示：

> **函数运行环境不可用**
>
> 声明有效，但当前本地安装没有已批准的函数运行时 Provider。

（服务端给出原因时，正文改为下表对应的文案。）这与「声明错误」是两回事——**声明是对的，是运行时没有**。
所以不要把这种情况当成 Manifest 写错了。

### 不可用原因

| 原因                   | 显示文案                                               | 含义                     |
| ---------------------- | ------------------------------------------------------ | ------------------------ |
| `RUNTIME_UNAVAILABLE`  | RUNTIME_UNAVAILABLE · 函数执行 Provider 尚未开放。     | 运行时未开放             |
| `FEATURE_UNAVAILABLE`  | FEATURE_UNAVAILABLE · 当前 profile 未开放此 Provider。 | 该类型的 Provider 不支持 |
| `MANIFEST_UNSUPPORTED` | MANIFEST_UNSUPPORTED · 仅支持查看 Manifest v2。        | Manifest 版本不对        |

### 关于 Provider

> **服务提供方**是函数或后台能力声明中关联的执行服务。
> **存在声明不代表当前运行时已启用或允许执行**，实际可用性由服务状态和授权决定。

Provider 有三种类型，写在 `manifest.json` 的 `backend.providers` 里：

| 类型               | 说明                                   |
| ------------------ | -------------------------------------- |
| `managed_function` | 由你的云函数实现                       |
| `logic_unit`       | 平台逻辑单元（声明式，不用写代码）     |
| `builtin`          | 平台内置动作，例如 `os.agent.complete` |

## 后台能力

切到「**后台能力**」标签页，这是**真正决定应用能不能在关窗后干活**的地方。

> **后台能力**是安装版本声明的、可在应用窗口关闭后运行的任务入口。
> 你需要**先允许后台运行**；每一步执行前仍会重新检查当前版本和授权。

### 页面布局

左边是**能力列表**，右边是选中能力的**详情**。

列表里每一项显示：

| 内容         | 说明                                                                  |
| ------------ | --------------------------------------------------------------------- |
| **能力标题** | Manifest 里能力的 `title`                                             |
| **影响**     | **只读** / **会写入数据**                                             |
| **触发器数** | 声明了触发器时显示「，N 个触发器」                                    |
| **状态点**   | 绿色 = 已允许后台运行；橙色 = 授权给了旧版本；灰色 = 未允许或不可运行 |

列表底部注明：「能力在 Manifest 中声明，随签名版本一起更新。」

空状态为「**这个版本没有声明后台能力**」，提示在 Manifest 的 `runtime.capabilities.provides`
中声明 `execution` 为 `headless` 的能力，签名新版本后会出现在这里。

### 详情头部

| 元素          | 说明                                                        |
| ------------- | ----------------------------------------------------------- |
| **标题与 ID** | 能力标题，下方是能力 ID，点击即可复制                       |
| **试运行**    | 主按钮，**只在已允许后台运行时出现**                        |
| **更多操作**  | 「…」菜单：**查看输入与结果**；已授权时还有**撤销后台授权** |

### 授权

头部下方是一条授权状态栏，根据当前状态显示不同内容：

| 状态               | 显示                                                                                     | 可做的操作          |
| ------------------ | ---------------------------------------------------------------------------------------- | ------------------- |
| **未允许**         | 「允许它在后台运行？」说明允许后关窗也能执行、可手动试运行或按触发器自动运行，随时可撤销 | **允许后台运行**    |
| **已允许**         | 「**已允许后台运行**」：授权给哪个版本，在开发环境中只处理你本人的数据                   | **撤销授权**        |
| **授权给了旧版本** | 「**授权给的是之前安装的版本**」：升级后权限可能不同，旧授权不再生效，已有触发器会暂停   | **重新授权**        |
| **不可运行**       | 「这个版本不能在后台运行这项能力」，并说明原因                                           | 无，需修改 Manifest |

「不可运行」有两种原因：

- Manifest 没有把这项能力声明为后台执行（`execution: "headless"`），或找不到它的执行方；
- Manifest 不是 `zleap.app/2` 格式。

授权只在三个限定条件同时成立时有效：**这个安装 + 这个版本 + 开发环境**，且只处理**你本人的数据**。

「允许后台运行」要求 Manifest 的 `background.modes` 包含 `"on_demand"`，否则服务端拒绝（「应用未声明后台按需执行」）。

> **授权与发布绑定**（提示）
>
> appid 应用：在这里点「允许后台运行」「撤销授权」「重新授权」，平台会同时把安装绑定到该版本的就绪发布
> （还没有就绪发布时当场补签），**不会解除发布绑定**，也不需要再去「激活开发」。
>
> 另一条路径是应用窗口顶部的「**权限**」：在其中勾选后台能力并「保存并重新加载」，
> 同样会把安装绑定到该版本的就绪发布（见[权限与授权](permissions.md)）。
> `logic_unit`、`builtin` 类型的能力在开发环境不需要绑定发布。

> **旧 app_key 应用：授权操作会解除发布绑定**（注意）
>
> 旧应用在这里点「允许后台运行」「撤销授权」「重新授权」，都会**解除安装上的已签名发布绑定**。
> 以 Node 云函数（`managed_function`）为执行方的能力随后会报 `FUNCTION_RELEASE_REQUIRED`，
> 需要到[版本与激活](console-legacy-release.md#激活开发)页再点一次「**激活开发**」。
> 安装已绑定发布时，确认框里会提前提示这一点；保存后面板顶部出现「**发布绑定已解除**」提示，侧栏「云函数」旁同步显示「未激活」。
>
> 「激活开发」**不要求**先允许后台运行，两者可以任意顺序完成；但只有两者都做了，后台能力才会真正执行。
> 因为允许 / 撤销会解除发布绑定，推荐顺序仍是：**先允许后台运行，再激活开发**，最后重新加载应用。

> **「关窗不取消后台授权」**（注意）
>
> 你关掉应用窗口，**不会**停止已批准的后台任务。这是设计如此——
> 否则用户随手关窗就会让定时任务失效。
>
> 但这也意味着：**如果你不想让某个后台任务继续跑，必须主动去撤销它。**

#### 允许时的确认

点击「**允许后台运行**」（或「**重新授权**」）会弹出确认框，标题为「允许「能力名」在后台运行？」
（重新授权时为「重新授权给 {版本}？」），正文**逐一列出它会访问的集合和动作**：

> 授权 {版本} 在开发环境中处理你本人的数据：`notes`（读取、修改）……
> 每一步执行前都会重新检查授权。**撤销后不会再开始新的步骤，已经写入的修改不会回滚。**

能力没有声明数据权限时，正文改为「授权 {版本} 在开发环境中以你的身份运行这项能力」。

#### 撤销时的确认

点击「**撤销授权**」或「更多操作 → **撤销后台授权**」：

> 撤销后不能再试运行，**它的触发器也会停止**，正在运行的调用会在当前步骤结束后停止。
> **已经写入的修改不会回滚。**

（没有声明触发器的能力不会提到触发器。）

> **「已经写入的修改不会回滚」**（危险）
>
> 这是分布式任务的基本事实：任务跑到一半，前面几步可能已经写库了。
> 撤销授权只能阻止**后续**步骤，无法撤回已完成的写入。
> 所以撤销后如果业务上需要一致性，你要自己去核对数据。

### 它能访问的数据

授权栏下方的「**它能访问的数据**」（标注「仅限你本人的记录」）列出这项能力声明的权限，
也就是授权时你同意的范围：

| 列       | 说明                                                                        |
| -------- | --------------------------------------------------------------------------- |
| **集合** | 集合名称                                                                    |
| **动作** | 读取 / 查询 / 计数 / 修改 / 覆盖 / 写入 / 新增 / 删除，**写入类动作会高亮** |
| **字段** | 允许访问的字段；未限定时显示「全部字段」                                    |

数据以外的权限会单独列在「**其他权限**」一行。

### 详情子标签

| 子标签         | 内容                                        |
| -------------- | ------------------------------------------- |
| **运行记录**   | 试运行和触发器产生的每一次调用              |
| **触发器**     | Manifest 为这项能力声明的触发器，用开关启用 |
| **输入与结果** | 能力的输入参数、返回结构和原始声明          |

## 试运行

已允许后台运行后，点击头部的「**试运行**」打开右侧抽屉，填写输入后点「**运行**」。

### 输入表单

表单根据能力的 `input_schema` 自动生成：

| Schema 类型        | 控件                                 |
| ------------------ | ------------------------------------ |
| 字符串、整数、数字 | 输入框，下方提示长度或取值范围       |
| 布尔               | 开关                                 |
| 枚举               | 选项不多时为分段按钮，较多时为下拉框 |
| 常量（`const`）    | 不需要填写，提示「… 会自动带上」     |

必填项标星号，非必填项提示「可选」。

抽屉右上角可以在「**表单**」和「**JSON**」之间切换，两边内容同步。
输入结构较复杂（嵌套对象、数组、组合类型）时**只能用 JSON 编辑**。
JSON 模式下输入框为「**输入（JSON 对象）**」，传给能力的参数对应云函数的 `event`：

```json
{ "ticket_id": "todo-001" }
```

输入整体**不能超过 64 KB**。

> **试运行是真实执行**（注意）
>
> 试运行**没有单独的确认框**。如果能力会写入数据，抽屉里会提示：
>
> > 会真实写入开发环境里的 {集合}。**关闭窗口不会中断已经开始的运行。**
>
> 点「运行」之前确认好参数。

提交后抽屉关闭，自动切到「运行记录」并展开这次运行。

### 还没收到确认的试运行

如果提交后没有收到服务端确认（例如网络中断），运行记录顶部会出现警告：

> **刚才的试运行还没收到确认**
>
> 它可能已经开始执行。为避免重复写入，确认之前不能再次试运行。

此时「试运行」按钮不可用，点警告里的「**查询结果**」按原操作编号查询，确认后才能再次试运行。

## 运行记录

空状态为「**还没有运行过**」：

- 已允许后台运行时提示「先试运行一次，确认输入和结果都符合预期，再去启用触发器。」并给出「试运行」按钮；
- 未允许时提示「允许后台运行后，可以在这里试运行并查看每次的结果。」

有记录时以表格展示，有执行中的记录会自动刷新（「运行中的记录会自动更新」）：

| 列       | 说明                                                                          |
| -------- | ----------------------------------------------------------------------------- |
| **状态** | 见下方[操作状态枚举](#操作状态枚举)                                           |
| **结果** | 执行中显示「已完成 n/m 步」或「等待执行」；失败显示错误码；成功显示返回值摘要 |
| **来源** | **试运行**，或触发器的名称（如「每天 03:00」）                                |
| **时间** | 相对时间，如「5 分钟前」「今天 03:00」，悬停显示完整时间                      |

行末的操作：

| 按钮         | 出现时机           | 作用                         |
| ------------ | ------------------ | ---------------------------- |
| **取消**     | 运行尚未结束时     | 停止还没开始的步骤           |
| **查询结果** | 状态为「结果未知」 | 对账，查明这次运行的真实结果 |

取消时的确认：

> 「还没开始的步骤不会再执行。**已经写入的修改会保留**，状态在当前步骤结束后更新。」

### 运行详情

点击一行展开详情：

| 区块                        | 说明                                               |
| --------------------------- | -------------------------------------------------- |
| **返回结果** / **失败原因** | 成功时列出返回值；失败时显示错误码                 |
| **执行步骤**                | 每一步的 ID 和状态；已写入的步骤会标注「已写入」   |
| **调用**、**操作编号**      | 可点击复制，排查问题或到日志（文档站 ./logs）里查询时使用 |

### 操作状态枚举

这是**最重要的一张表**，应用侧的 `job.status` 也是这套值：

| 状态               | 中文         | 含义                 | 能当成功吗 |
| ------------------ | ------------ | -------------------- | ---------- |
| `accepted`         | 已受理       | 请求已收到，尚未开始 | ❌         |
| `queued`           | 排队中       | 在队列里等           | ❌         |
| `running`          | 执行中       | 正在跑               | ❌         |
| `cancel_requested` | 取消确认中   | 已请求取消           | ❌         |
| `cancelled`        | 已取消       | 已取消               | ❌         |
| `succeeded`        | 执行成功     | 成功                 | ✅         |
| `failed`           | 执行失败     | 失败                 | ❌         |
| `unknown`          | **结果未知** | 无法判断             | ❌         |
| `revoked`          | 授权已撤销   | 授权没了             | ❌         |

**步骤状态**是另一套值：

| 状态        | 中文   |
| ----------- | ------ |
| `pending`   | 处理中 |
| `failed`    | 失败   |
| `committed` | 已提交 |
| `complete`  | 已完成 |

> **最常见的错误**（危险）
>
> **把 `accepted` 当成成功。** 它只表示「收到了」，任务可能后面才失败。
> 只有 `succeeded` 才是成功。
>
> 在应用代码里必须显式判断：
>
> ```js
> const job = await zl.cloud.os.capabilities.invoke({
>   id,
>   input,
>   operationId: op(),
> });
> if (job.status !== 'succeeded') {
>   throw new Error(job.errorCode || job.status);
> }
> ```
>

## 触发器

在能力详情里切到「**触发器**」子标签。这里**直接列出 Manifest 为这项能力声明的触发器**，
每个触发器一张卡片。触发器 ID、cron、时区、事件名**都来自 Manifest，不需要手填**，
你只需要决定开不开，以及填运行参数。

空状态为「**没有为这项能力声明触发器**」：在 Manifest 的 `triggers.scheduled` 或 `triggers.events`
中声明，并把 `capability` 指向这项能力，签名新版本后即可在这里启用。

还没允许后台运行时，卡片顶部提示「触发器会用这项能力的后台授权自动运行，先允许后台运行才能启用」，开关不可用。

### 卡片内容

| 内容           | 说明                                                                                                                   |
| -------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **标题**       | 定时触发器把 cron 翻译成人话，如「每天 03:00」「工作日 09:00」「每 30 分钟」；事件触发器为「收到 {事件名} 时」         |
| **规则**       | 定时：「{时区}，上一次没结束就跳过，错过的时间不补跑。」；事件：「同一事件重复投递只运行一次，只处理启用之后的事件。」 |
| **ID 与 cron** | 规则后面以等宽字体显示触发器 ID 和原始 cron 表达式                                                                     |
| **说明**       | Manifest 里的 `description`                                                                                            |
| **开关**       | **已启用** / **未启用**                                                                                                |

无法翻译成人话的 cron 会原样显示为标题。

事件名需匹配 `^[a-z][a-z0-9_.]{0,63}$`：小写字母开头，只能含小写字母、数字、`_` 和 `.`（**不能含 `-`**），例如 `my_app.scan.done`。详见触发器（文档站 /reference/triggers）。

规则里的几句话对应平台固定的默认策略：

| 策略                           | 含义                                   |
| ------------------------------ | -------------------------------------- |
| **上一次没结束就跳过**         | 上一次还没跑完，下一次不会启动         |
| **错过的时间不补跑**           | 服务不可用期间错过的时间点，不会补跑   |
| **同一事件重复投递只运行一次** | 同一条事件重复投递，不会产生第二次执行 |

### Cron 表达式怎么读

cron 在 Manifest 里声明，控制台只负责翻译和展示。
Cron 用**五个字段**描述执行时间，依次为**分钟、小时、日期、月份、星期**。
例如 `0 9 * * *` 表示按所选时区每天 09:00 触发。

```
┌─────────── 分钟 (0-59)
│ ┌───────── 小时 (0-23)
│ │ ┌─────── 日期 (1-31)
│ │ │ ┌───── 月份 (1-12)
│ │ │ │ ┌─── 星期 (0-6)
│ │ │ │ │
* * * * *
```

常用例子：

| 表达式         | 卡片标题       |
| -------------- | -------------- |
| `*/30 * * * *` | 每 30 分钟     |
| `15 * * * *`   | 每小时第 15 分 |
| `0 9 * * *`    | 每天 09:00     |
| `0 9 * * 1-5`  | 工作日 09:00   |
| `0 9 * * 1`    | 每周一 09:00   |

### 时区

时区决定定时规则按哪里的时间计算，取自 Manifest 里的 **IANA 时区名称**，
例如 `Asia/Shanghai` 表示中国标准时间。Manifest 没写时区时，按浏览器所在时区显示和保存。

### 启用

打开开关，会弹出「**启用「触发器名」**」抽屉：

> 每次触发都会用下面的参数运行一次，使用这项能力当前的后台授权。

抽屉和试运行是同一套表单：按能力的 `input_schema` 填写**运行参数**（可切换表单 / JSON），
会写入数据时同样有写入提示。填好后点「**启用触发器**」。

运行参数必须是**不超过 8 KB** 的 JSON 对象。

> **先试运行，再启用**（提示）
>
> 建议先在「运行记录」里用同样的参数试运行一次，确认输入和结果都符合预期，再启用触发器。

> **启用后不会补跑历史**（注意）
>
> 「只处理启用之后的事件」「错过的时间不补跑」意味着：启用之前的时段不会执行。
> 如果你期望「启用后立刻跑一次」，需要手动点「**试运行**」。

### 启用前的校验

启用时控制台会把触发器和 Manifest 再核对一次，不通过就在抽屉里提示原因：

| 提示                                                      | 原因                                         |
| --------------------------------------------------------- | -------------------------------------------- |
| 这个版本的 Manifest 不支持触发器。                        | Manifest 不是 `zleap.app/2`                  |
| Manifest 没有在 background.modes 中开启这种触发方式。     | `background.modes` 缺少对应模式              |
| Manifest 中找不到这个触发器，或声明重复。                 | 触发器 ID 不存在或重复                       |
| 这个触发器在 Manifest 中绑定的是另一项能力。              | `capability` 指向了别的能力                  |
| 只支持「禁止重叠、错过跳过」的触发策略，请修改 Manifest。 | `overlap` / `misfire` 不是 `forbid` / `skip` |
| 定时规则与 Manifest 声明不一致。                          | cron 或时区对不上                            |
| 事件与 Manifest 声明或订阅不一致。                        | 事件名不一致，或没在 `events.subscribes` 里  |
| 运行参数必须是不超过 8 KB 的 JSON 对象。                  | 运行参数超限                                 |

### 已启用的触发器

开关打开后，卡片展开两栏：

| 区块             | 说明                                                                |
| ---------------- | ------------------------------------------------------------------- |
| **接下来**       | 定时触发器**接下来最多 5 次**的运行时间；事件触发器显示「等待事件」 |
| **修改运行参数** | 重新打开抽屉，保存后替换当前参数，**从下一次触发开始生效**          |
| **最近投递**     | 最近 5 次投递的时间和状态；还没投递过时显示「还没有投递过。」       |

> **用「接下来」核对 cron 和时区**（提示）
>
> cron 和时区出错时往往不会报错，只是触发时间不符合预期。
> 启用后**看一眼「接下来」的时间**是不是你想要的。

投递状态分三类：

| 类别   | 状态                       |
| ------ | -------------------------- |
| 进行中 | 等待投递、重试中、已受理   |
| 成功   | 已投递、已完成             |
| 失败   | 投递失败（同时显示错误码） |

每条投递后面的操作：

| 按钮         | 出现时机               | 作用                                 |
| ------------ | ---------------------- | ------------------------------------ |
| **查看运行** | 投递已产生调用         | 跳到「运行记录」并展开对应的那次运行 |
| **重新投递** | 投递彻底失败（`dead`） | 对这次失败的投递重新发起投递         |

> **重新投递不会重复写入**（提示）
>
> 「重新投递」针对的是原来那次投递：平台复用原调用，**不会重跑结果未知的写入**。
> 这符合平台的一贯原则：不重复执行可能有副作用的操作。

### 停用

关闭开关会确认：

> 「停用「触发器名」？之后不会再自动运行。**正在运行的那一次不受影响。**」

## 常见问题

### 函数列表是空的

「当前活跃版本未声明云函数。」检查 `manifest.json`：

- `runtime.backend.functions` 是否有内容；
- 上传的是不是**最新版本**（控制台读的是你作为发布者拥有的最新 Manifest）。

### 函数状态一直是「已声明」，不是「可调用」

安装还没有绑定已签名发布。

- appid 应用：上传时自动签名、安装和切换版本时自动绑定，正常情况下不会停在这里。在应用窗口「权限」里重新保存一次，
  或在「版本管理」里切换一次版本，平台会自动补签并绑定。只有 `zleap-app diagnose` 提示 `next_action: app_prepare` 时，
  才需要兜底运行 `zleap-app prepare`（只准备开发环境，不碰生产）。线上用户由「发布为线上版本」自动准备。
- 旧 `app_key` 应用：到[版本与激活](console-legacy-release.md)完成「验证并签发」和「激活开发」。

### 试运行或 `callFunction` 报 `FUNCTION_RELEASE_REQUIRED`

Node 云函数只运行绑定了就绪签名发布的版本。

- appid 应用：正常情况下不会出现（上传自动签名 + 随用随签）。如果出现，在应用窗口「权限」里重新保存一次，
  或在「版本管理」切换一次版本，平台会自动补签并绑定；仍然出现，说明部署的发布签名不可用（联系平台管理员检查签名密钥 / 信任配置），或重新上传。
- 旧 `app_key` 应用：常见原因是还没激活，或激活后又在这里改过后台授权（会解除绑定）。
  到[版本与激活](console-legacy-release.md#激活开发)页完成「验证并签发」和「激活开发」，然后重新加载应用。

### 「后台能力」里看不到我的能力

- 能力的 `execution` 是否为 `headless`；
- 是否声明在 `runtime.capabilities.provides` 里；
- 是否已签名新版本并安装。

### 显示「授权给的是之前安装的版本」

你升级了应用版本，旧授权不再对新版本生效，已有触发器也会暂停。
核对「它能访问的数据」后点「**重新授权**」。

### 触发器卡片是空的

「没有为这项能力声明触发器。」检查 Manifest：

- `triggers.scheduled` 或 `triggers.events` 里是否有这个触发器；
- 它的 `capability` 是否**正好指向这项能力**（指向别的能力的触发器显示在别的能力下面）。

### 启用触发器时报错

控制台会把触发器和 Manifest 逐项比对，看抽屉里的提示，对照[启用前的校验](#启用前的校验)修改 Manifest，
签名新版本后再启用。常见的是：

- `background.modes` 里没有 `"scheduled"`（或 `"events"`）；
- 声明了 `overlap` / `misfire`，但不是 `forbid` / `skip`；
- 事件触发器监听的事件没有写进 `events.subscribes`。

### 「试运行」按钮是灰的

运行记录顶部有「刚才的试运行还没收到确认」时，先点「**查询结果**」。
确认原来那次的结果之前不能再次试运行，以免重复写入。

### 云函数报 `RUNTIME_GATEWAY_UNAVAILABLE` 或其他 `RUNTIME_GATEWAY_*`

云函数里读写数据库要经过运行时数据网关。`RUNTIME_GATEWAY_UNAVAILABLE` /
`RUNTIME_GATEWAY_ADMISSION_REQUIRED` 表示当前部署的函数节点没有接入网关，属于平台侧问题，请联系运维；
`RUNTIME_GATEWAY_EXPIRED`、`RUNTIME_GATEWAY_TOKEN_INVALID` 等表示本次调用的网关凭据过期或无效，重新发起调用即可。
平台会**明确失败**，而不是用假数据冒充成功。

### 关窗后任务还在跑

预期行为。要停止它，在能力详情里点「**撤销授权**」（它的触发器会一起停止），
或到「触发器」子标签里关掉对应触发器的开关。
