# 从开发到上线

这一篇把一个应用从**写第一行代码**到**同事们在生产环境里用上**的全过程串起来。
每个阶段只讲「做什么、在哪做、做完的标志」，细节链接到对应页面。

如果你只想先在自己桌面上跑通一个读写数据库的应用，先看 快速开始（文档站 /guide/quickstart）。

## 九个步骤

```
创建应用（拿 appid）
        ↓
脚手架新建项目 / 已有项目接入
        ↓
npm run login → npm run deploy（构建 → 检查 → 上传开发版本 → 装到自己桌面）
        ↓                         ↘ 声明了集合：安装时自动开通开发环境、数据库、集合
        ↓                         ↘ 声明了后台能力：上传时自动签名，安装时自动绑定
打开应用调试（运行体检、控制台日志、npm run logs）
        ↓
有后台能力？→ 应用窗口「权限」里允许后台运行
             （定时触发器在控制台「触发器」里启用）
        ↓
任一成员发布为线上版本（首次带云资源时平台自动准备生产）
        ↓
同事在应用中心安装；下次打开自动更新，非成员 24 小时后强制更新
        ↓
迭代：deploy → release；回退：把旧版本再 release 一次
        ↓
一起开发：控制台「成员」里添加开发者
```

### 第 1 步：创建应用，拿到 `appid`

**做什么**：在云开发控制台新建一个应用，拿到平台生成的 `appid`（应用标识，`zl` + 16 位小写十六进制）。

**在哪做**：打开启动台 →「更多工具」→「云开发控制台」（也可以在启动台直接搜索「云开发」）。
云开发控制台是**系统内置应用**，不需要去应用中心安装。在左上角应用切换器里点「**创建应用**」，填应用名称（说明可选），点「创建」。

**做完的标志**：控制台概览显示这个应用的 `appid`，并提示「应用已创建，还没有上传过代码。按下面三步把第一个版本传上来。」
你自动成为应用**管理员**；要加同事一起开发，去「成员」页（见第 9 步）。

（截图：新建应用、还没上传时的控制台概览，见文档站）

### 第 2 步：生成项目，或接入已有项目

**做什么**：准备一个能部署到 zleapOS 的项目，并让 `manifest.json` 指向第 1 步的 `appid`。

**在哪做**：

- **新项目**：用脚手架生成 React + TypeScript + Vite 项目：

  ```bash
  npm create zleap-app@latest my-app -- --appid <appid> --name "我的应用"
  ```

  生成的项目自带 Cloud SDK、`zleap-app` CLI、部署脚本和 AI 编程工具 skills。详细选项见 npm 包与工具链（文档站 /guide/npm-packages#脚手架-create-zleap-app）。
  需要 Node.js 20.19.x 或 22.12+，安装步骤见 环境准备与安装（文档站 /guide/install）。

- **已有项目**：把 `appid` 写进 `manifest.json` 的 `appid` 字段，
  并参考 已有项目接入云开发（文档站 /guide/integrate） 配置 SDK、构建和部署脚本。

**做完的标志**：`manifest.json` 里有正确的 `"appid": "zl…"`；本地 `npm run dev` 能打开页面。

### 第 3 步：登录并部署到自己的桌面

**做什么**：登录开发会话，构建、检查、上传一个开发版本，并把它安装 / 切换到自己桌面。

**在哪做**：项目目录里执行：

```bash
npm run login -- --target https://os.example.com
# 浏览器打开后，核对页面与终端里的确认码一致，再点「允许开发工具」

npm run deploy
# 构建 → 检查 → 上传开发版本 → 安装 / 切换本人安装
```

- 登录后的**访问凭据 30 分钟有效，CLI 会自动续期**；授权从首次登录起最长 30 天。
- `npm run deploy` 上传的是**开发版本**，只有应用成员能看到和安装，还不是线上版本。
- 声明了 `data.collections` 的应用，安装时平台会**自动创建开发环境、开通数据库、按 Manifest 建集合**，通常 1 分钟内完成。
- 声明了后台（headless）能力的版本，平台在**上传时自动签名**，安装 / 切换到这个版本时自动绑定，不需要手动签名。

**做完的标志**：终端输出 `app_id`、`version_id`，并提示「本人安装已是 v…」；控制台概览的开通清单三步
（创建开发环境、开通数据库、创建集合）全部完成。开通清单只有这三步。

> **开通没有自动完成时**（提示）
>
> 声明了集合的应用，安装时平台会自动创建开发环境、开通数据库并按 Manifest 建集合。如果概览停在数据三步：
> 第 1 步没完成就选「来源版本」点「**创建开发环境**」；数据库失败时点「查看并重试」；集合缺失时点「**同步集合**」→「同步 Manifest 中的集合」。

> **版本号会自动递增**（提示）
>
> `npm run deploy` 发现同一个 `version` 已经上传过不同内容时，会自动把补丁号加一。你也可以手动改 `manifest.json` 的 `version`。

### 第 4 步：打开应用，调试

**做什么**：从启动台打开应用，确认它连上了 OS、能读写数据，并学会看运行状态和日志。

**在哪做**：

- 启动台打开刚安装的应用。应用窗口顶部有「**权限**」和「**重新加载应用**」；左下应显示「**● OS 已连接**」。
- 控制台「概览」里的「**运行体检**」会逐层检查安装、授权、数据和后台能力，失败时给出具体层。
- `npm run status` 等价于 `zleap-app diagnose <app_id>`，查看安装版本、权限和开通状态。

调试工具：

| 想看什么           | 用什么                                                                                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 哪一层没通         | 控制台概览「**运行体检**」逐层检查；命令行 `zleap-app diagnose <app_id>`                                                                                           |
| 数据写进去没有     | 控制台「数据库」，选集合看文档（显示该环境所有使用者的数据）                                                                                                       |
| 文件               | 控制台「文件存储」                                                                                                                                                 |
| 后台调用为什么失败 | 「云函数」页运行记录复制调用编号 →「日志」页「按调用编号查询」（发布者能看到所有人的调用日志）                                                                     |
| 直接试调后台能力   | `zleap-app invoke <app_id> --capability <能力 ID> --environment dev --input-file in.json`，再用 `zleap-app invocation <app_id> <调用编号>` 查结果                  |
| 应用页面报了什么错 | `npm run logs`（等价于 `zleap-app runtime-logs <app_id> --environment dev`）：本人最近 24 小时、最多 200 条页面结构化错误，外加本人的云函数日志（`function_logs`） |

**做完的标志**：应用窗口能正常读写；运行体检显示各层通过；日志里没有持续报错。

**验收**——「能打包」「能上传」「能用」是三件事。`check`、`prepare` 成功都只是 `runtime_test=not_checked`。
要证明应用真的能用，可以用 `zleap-app test` 跑一次真实浏览器验收：

- 运行机预先装好 Node.js 22.12+、Puppeteer Core 25+ 和 Chrome，准备一个仅属主可读写（0600）、放在仓库外的运行配置；
- 验收计划（JSON）固定 `app_key`（填应用标识，即 `appid`）、`version_id` 和 `steps`，**必须**包含读取断言、写操作、独立数据探针和刷新后断言；
- 命令是 `zleap-app test <plan.json> --runner-config <运行器配置>`，第一个参数是**计划文件**，不是应用目录；
- 报告用 `zleap-app logs <report_id>` 查看。只用专用测试账号和测试数据。

#### 验收计划怎么写

验收由运维或你本人在本机准备的「运行器」执行，分两份文件：运行器配置（含测试账号，只放本机）和验收计划（描述要点什么、核对什么）。
AI 工具通过 MCP 调用时用同一份运行器配置：启动 `zleap-app mcp serve` 时加 `--runner-config`，再用 `app_test` 提交计划。

**运行器配置**：JSON 文件，权限 0600，放在应用目录之外，绝不能打进应用包。

| 字段                                  | 说明                                                                                                                                                   |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `node`、`puppeteer_module`、`browser` | Node.js（≥ 22.12）、Puppeteer Core（≥ 25）入口和 Chrome 可执行文件的绝对路径                                                                           |
| `auth_file`                           | 测试账号认证 JSON 的绝对路径（含 `access_token`，可含 `refresh_token`，0600）。由你用专用账号正常登录获得，只给运行器读取，不能放进 MCP 参数或交给应用 |
| `os_url`、`target`                    | 目标 OS 地址                                                                                                                                           |
| `app_key`                             | 固定为本应用（appid）                                                                                                                                  |
| `app_id`、`app_name`                  | 可留空，由当前会话的发布记录按不可变 `version_id` 解析                                                                                                 |
| `allow_mutation`                      | 必须显式写 `true`，表示允许验收写入专用测试数据                                                                                                        |
| `probes`                              | 探针名到同一部署只读 API 路径的映射，例如 `{"todos": "/api/v1/…"}`；参数按 `app_api_get` 查到的契约填写                                                |

测试账号必须和开发会话是同一个账号。可用的探针名可以用 `app_caps_get` 查看（`acceptance_runner.configured` 与 `probe_names`），
计划里只能引用这里配置过的探针，不接受应用传入新的 URL、身份、脚本或浏览器跳转。

**验收计划**：`app_key`、`version_id` 和 4 到 128 个 `steps`。每一步都要写 `phase`，取值 `read`、`write` 或 `persistence`；
`target` 可选 `app`（应用窗口内）或 `host`（宿主页面）。可用的动作：

| 动作                      | 必填字段                                                     | 说明                                                                                       |
| ------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| `click`、`fill`、`select` | `selector`                                                   | 交互，`fill` / `select` 用 `value` 给出要填或要选的值；放在 `write` 阶段时算一次真实写操作 |
| `click_text`              | `text`                                                       | 按文字点击                                                                                 |
| `assert_text`             | `text`                                                       | 页面出现指定文字                                                                           |
| `assert_count`            | `selector`、`count`（0–10000）                               | 匹配元素的数量                                                                             |
| `assert_image`            | `selector`                                                   | 图片必须真正解码成功、宽高非零，只检查有 `img` 标签不算通过                                |
| `probe`                   | `probe`，以及 `expected` 或非空 `contains`（可配 `pointer`） | 用运行器配置里的探针独立读取数据核对                                                       |
| `reload`                  | —                                                            | 刷新页面                                                                                   |

编排规则，运行器会逐条校验：

1. 必须有 `read` 阶段的断言。
2. 必须有 `write` 阶段的真实写操作，并在写之后用 `probe` 独立核对数据。
3. `reload` 只能放在写操作和写后探针之后。
4. `persistence` 阶段的断言必须在 `reload` 之后，证明刷新后数据还在。

示例（待办应用：读取列表，新增一条，探针核对，刷新后确认还在）：

```json
{
  "app_key": "<appid>",
  "version_id": "<要验收的版本 ID>",
  "steps": [
    { "phase": "read", "action": "assert_text", "target": "app", "text": "待办" },
    {
      "phase": "write",
      "action": "fill",
      "target": "app",
      "selector": "input[name=title]",
      "value": "验收-001"
    },
    { "phase": "write", "action": "click_text", "target": "app", "text": "添加" },
    { "phase": "write", "action": "probe", "probe": "todos", "contains": "验收-001" },
    { "phase": "persistence", "action": "reload" },
    { "phase": "persistence", "action": "assert_text", "target": "app", "text": "验收-001" }
  ]
}
```

选择器和文字按你自己的页面填写，动作名以 `app_spec_get(section=acceptance)` 返回的 schema 为准。
报告 `status` 为 `passed` 且 `browser_tested` 为 `true` 才算通过。验收期间如果版本发生变化，结果作废，需要重新验收。

（截图：部署后的应用窗口：OS 已连接，能读写待办，见文档站）

> **开发环境只对应用成员开放**（说明）
>
> 开发数据域对**全部应用成员**（管理员 / 开发者）开放：在「成员」里加为开发者的同事装上开发版本，就能和你一起读写开发数据。
> 非成员访问会被拒绝（`PUBLISHER_REQUIRED`，「开发环境仅发布者本人可访问」）——要给他们用，请发布为线上版本（第 6 步）。

### 第 5 步：有云函数 / 后台能力时，允许后台运行

**做什么**：让云函数和后台能力在开发环境里真正跑起来。只有 Manifest 声明了云函数、`runtime.backend` 或 `execution: "headless"` 的后台能力时才需要；
只用宿主能力的应用直接跳到第 6 步。

不需要手动签名：带后台能力的版本在上传时已由平台自动签名；安装、切换版本、在「权限」里保存、在控制台「云函数」页允许 / 撤销后台运行时，
平台都会把你的安装绑定到该版本的就绪发布。改动前上传的旧版本、上传时签名失败的版本，也会在这些时机当场补签再绑定。

**在哪做**：

1. 打开应用窗口，点「**权限**」，在「**应用权限**」对话框里勾选「**后台能力（定时任务 / 云函数）**」下要用的能力，
   点「**保存并重新加载**」。后台能力必须由**使用者本人**授权，这一步不能省。
2. 有定时触发器的，在控制台「**触发器**」里启用（或由使用者开启 `user_configurable` 的定时任务）。

**做完的标志**：「云函数」页对应函数状态为「**可调用**」；应用窗口「权限」里不再出现「该版本还没有可用的签名发布，暂时无法执行。……」的提示。

> **调用报 FUNCTION_RELEASE_REQUIRED**（提示）
>
> 正常情况下不会出现。如果出现：在应用窗口「权限」里重新保存一次，或在控制台「版本管理」点一次「切换到此版本」，平台会自动补签并绑定；
> 仍然出现，说明部署的发布签名不可用（请平台管理员检查签名密钥 / 信任配置），或重新上传这个版本。

#### 兜底准备 `prepare` {#prepare}

`prepare` **只准备开发环境，不碰生产**，通常不需要运行；只有 `zleap-app diagnose` 提示 `next_action: app_prepare` 时才用它兜底：
依次执行 `dev_environment` → `database_allocation`（声明了数据时）→ `declared_permissions`（开发数据域权限，并启用调用者本人安装的全部已声明 headless 后台能力）；
声明了 headless 后台能力时，平台随后完成签名并绑定到**开发**。响应里 `"environment": "dev"`；
只声明数据的应用返回 `status: "ready"`；完全没有声明云资源时返回 `status: "not_required"`。

```bash
zleap-app prepare <app_id> --version-id <version_id> --request-id $(openssl rand -hex 16)
```

`--request-id` 是幂等键，不传时命令行自动生成（32 位小写十六进制）；**结果未知时用同一个编号重试**。
`prepare` 只接受**本人上传的版本**，传别人的 `version_id` 会得到 403「只能准备本人上传的版本」。
成功同样只是 `runtime_test=not_checked`；生产由第一次「发布为线上版本」自动准备。

### 第 6 步：发布为线上版本

**做什么**：把某个开发版本设为线上版本，让全企业用户可以用到。

**在哪做**：控制台侧栏「发布」→「**版本管理**」，在要上线的版本行点「**发布为线上版本**」（可填「发布说明（可选）」）。
**任一成员都可以发布任一版本**，包括同事上传的版本。
也可以在项目里发布最近一次 `npm run deploy` 上传的版本：

```bash
npm run release -- --notes "本次更新说明"
# 交互环境会二次确认；CI 等非交互环境加 --yes
# 等价于 zleap-app release <app_id> --version-id <version_id> --notes "…"
```

发布后**全企业可见**：应用出现在应用中心，新安装装的是线上版本。

| 版本类型                                               | 发布时平台做什么                                                                                                                                              |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **只用宿主能力**（没有集合、`cloud.*` 能力、后台能力） | 直接发布，发布即可用。不需要签名，也不需要开发 / 生产环境                                                                                                     |
| **带云资源**（声明了集合、`cloud.*` 能力或后台能力）   | 第一次发布时自动完成**应用级**生产准备：生产环境 → 签发生产发布（归属上传者）→ 生产门禁（签名、审批窗口、信任策略核对）→ 生产库与生产集合。不依赖任何人的安装 |

已经发布过的版本再次发布（包括回退）直接复用当时的就绪发布。

> **部署没开放生产时**（说明）
>
> 带云资源的版本第一次发布会卡在准备生产（生产环境建不出来）。这是**部署未开放生产**，由运维决定，不是你的应用写错了；
> 只用宿主能力的应用不受影响。控制台侧栏出现「开发环境 / 生产环境」切换，说明生产已开放；没有这个切换就是未开放，拿不准时问部署方。

**做完的标志**：「线上版本」卡片显示这个版本；应用中心能搜索到应用；同事可以安装。

> **应用中心「我的发布」里的版本**（提示）
>
> 版本行显示「**仅成员可见**」，卡片统计是「企业 n / 开发版本 n」。成员版本的主按钮是「**去版本管理发布**」，点它打开云开发控制台「版本管理」；
> 已发布的版本显示「**企业可见**」并保留「**云开发**」按钮。上线统一在「版本管理」里点「发布为线上版本」。

> **第一次发布没成功**（提示）
>
> 带云资源的版本第一次发布可能返回 40900（看 `detail.reason`）：
>
> - `PROD_DATABASE_NOT_READY`「生产数据库还没就绪，暂时不能发布」：通常 1 分钟内就绪，稍后在「版本管理」里重新发布；持续失败请在控制台「数据库」查看状态。
> - `UPLOADER_INACTIVE`「这个版本的上传者账号已停用，无法发布」：请其他成员重新上传这个版本（`npm run deploy`）后再发布。
> - 生产门禁不通过（如 `RELEASE_APPROVAL_EXPIRED_OR_MISSING`、`RELEASE_POLICY_STALE`、`PRODUCTION_RELEASE_UNAVAILABLE`）：重新发布即会重新签发。

### 第 7 步：同事安装，之后自动更新

**做什么**：让同事在应用中心安装，并理解后续更新行为。

**在哪做**：同事打开「应用中心」→「发现」，找到应用并点「安装」。安装时会一次性授予该版本 Manifest 声明的数据 / 文件权限；
**后台能力仍需同事本人在应用窗口「权限」里勾选**。

**做完的标志**：同事能打开应用并读写**生产数据域**。开发环境里的数据不会带过去。

更新行为：

- 发布新线上版本后，没开着应用的使用者**下次打开自动更新**；
- 正开着旧版本的窗口会收到更新提示；
- **非成员**的旧窗口在新版本发布 **24 小时后会被强制切换**，提示「这个版本已超过 24 小时的使用期限，正在更新到最新版本…」；
- 应用里也可以用 `zl.app.getUpdateManager()` 主动提示立即更新。

详见 [版本管理](console-release.md) 和 版本更新与授权登录（文档站 /reference/app-runtime）。

### 第 8 步：迭代与回退

**做什么**：持续发新版本；出问题时回到旧版本。

**在哪做**：

- **迭代**：改代码 → `npm run deploy` 上传新开发版本 → 在「版本管理」或 `npm run release` 发布它。
- **自己先换到某个版本**：在「版本管理」里点「**切换到此版本**」（只切你自己桌面上的应用，不影响其他人，也不改变线上版本），或
  `zleap-app update <app_id> --expected-version-id <当前> --version-id <新>`。
- **回退**：在旧版本行点「**回退到此版本**」，或 `zleap-app release <app_id> --version-id <旧版本 ID>`。

> **回退应用版本不等于回退业务数据**（危险）
>
> 「回退到此版本」只改线上版本，**不会回退数据库里的数据**。目标版本的 `data` / `storage` 声明与当前版本不同时，
> `update` / `rollback` 会返回 `DATA_MIGRATION_REQUIRED` 并保持原版本；平台不会替你做数据迁移。

> **集合结构不会随新版本更新**（注意）
>
> 集合在开发环境数据库就绪后按 Manifest 自动创建；之后**新版本改 Schema 不会更新已有集合**。
> 需要调整结构时，新建一个集合并自行迁移数据。

### 第 9 步：一起开发

**做什么**：让同事能上传、调试和管理这个应用。

**在哪做**：控制台侧栏「团队」→「**成员**」→ 输入对方的登录名、手机号或邮箱，角色选「**开发者**」，点「添加」。
角色说明：**管理员**「管理成员与应用」；**开发者**「上传、调试与管理」。只有管理员能增删成员。

**做完的标志**：成员列表出现同事；同事用同一 `appid` 登录后，可以 `npm run deploy`，他上传的版本也会出现在「版本管理」里，
任何成员都可以把合适的版本发布为线上版本。

> **成员共享开发数据**（提示）
>
> 成员装上开发版本后使用的是同一个开发数据域，彼此能看到对方在共享集合里写的数据（私有集合按账号隔离）。

## 上线前检查清单

| 检查项                                                         | 怎么做                                                                   |
| -------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Manifest 的集合结构已定稿（之后不能改）                        | 检查 `manifest.json`                                                     |
| `check --target` 在目标部署上通过                              | 命令行（需先登录）                                                       |
| （声明了集合时）开通清单的数据 3 步完成，运行体检全部通过      | 控制台概览；安装后通常自动完成，必要时手动创建 / 同步                    |
| （有后台）版本已签名并绑定、后台能力已允许，函数状态「可调用」 | 应用窗口「权限」允许后台运行；必要时重新保存或切换版本，让平台补签并绑定 |
| 用同一版本完成了真实读写验证（手动或 `zleap-app test`）        | 应用窗口 / 验收报告                                                      |
| （生产已开放时）生产环境与集合已准备好                         | 首次「发布为线上版本」自动完成                                           |
| 已发布给同事，同事安装后能打开并读写                           | 「版本管理」→「发布为线上版本」（应用中心「发现」安装）                  |

## 常见卡点

| 现象                                               | 原因                                                             | 处理                                                                                                                                   |
| -------------------------------------------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 上传报 40400「appid 不存在」                       | `appid` 还没在控制台创建，或抄错了                               | 先在云开发控制台「创建应用」，复制它的 `appid`                                                                                         |
| 上传报 40300「你不是这个应用的开发者」             | 你不是这个应用的成员                                             | 请应用管理员在控制台「成员」里把你加为开发者                                                                                           |
| `prepare` 报 403「只能准备本人上传的版本」         | 传了别人上传的 `version_id`                                      | 只准备本人上传的版本                                                                                                                   |
| 发布报 `PROD_DATABASE_NOT_READY`                   | 带云资源的版本第一次发布，生产数据库还没就绪                     | 通常 1 分钟内就绪，稍后重新发布；持续失败到控制台「数据库」查看状态                                                                    |
| 发布报 `UPLOADER_INACTIVE`                         | 这个版本的上传者账号已停用                                       | 请其他成员重新上传这个版本（`npm run deploy`）后再发布                                                                                 |
| 同事在应用中心看不到某个开发版本                   | 开发版本可见性为 `members`，只有应用成员能看到                   | 把同事加为开发者；要给全企业用，在控制台「版本管理」发布为线上版本                                                                     |
| 应用中心显示「暂不可用」                           | 申请了白名单外的能力、`host_api.profile` 不是 `app-runtime/2` 等 | 应用中心 · 暂不可用（文档站 /app-center/overview#「暂不可用」是什么意思）                                                                     |
| 应用打开报「连接需要处理」/ `RESOURCE_NOT_READY`   | 当前数据域没有环境或数据库未就绪                                 | 完成第 3 步；生产已开放时检查首次「发布为线上版本」是否完成生产准备                                                                    |
| `SCOPE_FORBIDDEN`（服务端原因 `CONSENT_REQUIRED`） | 「权限」里的应用权限一项都没勾                                   | 勾选后「保存并重新加载」                                                                                                               |
| `PUBLISHER_REQUIRED`                               | 非成员访问开发数据域                                             | 把对方加为开发者，或发布线上版本后走生产数据域                                                                                         |
| `FUNCTION_RELEASE_REQUIRED`                        | 云函数所在版本没有绑定就绪发布                                   | 在应用窗口「权限」重新保存一次，或在「版本管理」点一次「切换到此版本」，平台自动补签并绑定；仍出现请平台管理员检查签名配置，或重新上传 |
| `ENV_FORBIDDEN`（同事打不开）                      | 生产已开放，但应用还没有生产环境                                 | 先发布线上版本                                                                                                                         |
| `COLLECTION_NOT_FOUND`                             | 生产数据域里还没有集合                                           | 检查 `data.collections`，并在控制台「数据库」查看生产库状态                                                                            |
| 首次「发布为线上版本」卡在准备生产                 | 部署未开放生产，带云资源的版本建不出生产环境                     | 联系运维开放生产；只用宿主能力的应用不受影响                                                                                           |
| `COMMIT_UNKNOWN` / 「结果待确认」                  | 网络中断，服务端可能已处理                                       | 用原操作号查询结果，**不要换个编号重新提交**                                                                                           |

完整错误码见 [状态与错误码](status-codes.md)，平台未开放的能力见 平台边界与限制（文档站 /reference/limits）。
